# `data/` — what is committed, what is regenerable, what is irreplaceable

Most of `data/` is gitignored (`/data/*`) because it is regenerated by the engine. What survives
git does so by an explicit `!` whitelist, and each whitelisted file falls into exactly one of three
classes. **The class matters: it tells a future rebuilder whether a missing file is an inconvenience
or a permanent loss.**

## Class 1 — CARRIED IRREPLACEABLE (committed; cannot be reproduced)

These were built by a one-time scrape of a live third-party site. The producer script still exists,
but re-running it does **not** reproduce the file: the source restates figures, and pages for
delisted names disappear entirely. Losing one of these loses evidence, not just time.

| file | sha256 | producer (non-reproducing) | what depends on it |
|---|---|---|---|
| `fundamentals_pit_screener.pkl` | *(see `git log` for the commit that added it)* | `scripts/scrape_screener.py` | the solvency filter (D/E < 1.5) — BUILD_SPEC §2 |
| `fundamentals_pit_depth.pkl` | `018fd398fd659a5d202954004d19be6afe65b45363e4a7097c8019ce005da677` | `scripts/scrape_screener.py --mode all --out data/fundamentals_pit_depth.pkl --no-merge first` | findings [0019](../research/findings/0019-fundamentals-depth-ic.md) (depth IC) and [0108](../research/findings/0108-fundamental-growth-filter.md) (growth filter, KILL); `forward/prereg.md` §rev_yoy |

`fundamentals_pit_depth.pkl` is a dict of **653 tickers** (496 then-current + 211 recovered from the
delisted cache), Screener-sourced annual P&L, ~2018–2026, PIT-clean by construction
(availability = `period_end + 90d`, strict-before joins; truncation-tested by
`tests/test_fundamentals_pit_depth.py`).

**Why committed rather than attached to the dataset release.** The 2026Q3 verification audit (gap
**G3**, ledger row **D4**) found this file in *neither* git nor any release — it existed only on the
owner's laptop, and the clean-clone disaster drill could not have rebuilt findings 0019 or 0108. At
1.2 MB it is small enough to track directly, which is strictly better than a release asset: the
clean clone gets it for free, with no `gh release download` step and no chance of the pin and the
asset drifting apart. This mirrors how `fundamentals_pit_screener.pkl` has always been handled.

Verify either file with:

```bash
python -c "import hashlib,pathlib;print(hashlib.sha256(pathlib.Path('data/fundamentals_pit_depth.pkl').read_bytes()).hexdigest())"
```

## Class 2 — CARRIED CORRECTIONS (committed; hand-built, cheap to re-verify)

`nifty500_membership.csv`, `nifty500_official_20250720.csv`, `delisted_alias_map.json`,
`corporate_actions_demergers.csv`, `problem_sector_map.json`, `nse_circulars/`,
`ohlcv_backfill_manifest.json`, `macro_data.pkl`, `sector_intelligence.pkl`.

These encode research decisions (index membership reconstruction, demerger handling, sector fixes).
They are committed because they are *judgements*, not outputs.

## Class 3 — REGENERABLE (gitignored; rebuild, don't hunt)

`ohlcv.pkl`, `ohlcv_backfill.pkl`, `features.pkl`, `_screener_cache/`.

`ohlcv.pkl` is the 64 MB pinned price history — too big for git, and **release-pinned** instead
(`gh release download dataset-pin-20260701`, sha256 prefix `f8625a8f…`). It is the one regenerable
file whose exact bytes matter, which is why it has a pin rather than a rebuild instruction. See
[docs/DATA_AND_ARTIFACTS.md](../docs/DATA_AND_ARTIFACTS.md) §4a.

## The rule this file exists to enforce

A number that informs a decision must be reproducible from the committed pipeline. That is
impossible if an input lives only on one machine. **Before relying on a new `data/` file in a
finding, place it in one of the three classes above and record it here** — the audit's most
expensive discoveries were all files nobody had noticed were unbacked.
